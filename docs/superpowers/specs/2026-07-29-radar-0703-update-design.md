# 0703 雷达与 SLAM 更新设计

## 目标

将 `G:\泊位检测\0703` 中的新版雷达相关能力选择性迁移到当前工程：

1. 接入新版 `LidarGnssSlam` 的组合导航预测、GICP 协方差估计和误差状态卡尔曼更新。
2. 保留 `201/213/214` 雷达的数据接收、解析和工作线程，但不让它们进入当前融合点云。
3. 使用 `refined_211_T_210(1).txt` 更新 210 与 211 雷达之间的外参，并保证所有调用方使用同一坐标约定。

## 外参约定

项目统一采用：

```text
p_B = T_A_to_B * p_A
```

文件名 `refined_211_T_210` 按常用标定命名表示 `p_211 = T_211_210 * p_210`，因此其矩阵写入项目的 `T_210_to_211`：

```text
0.7549675755  0.6556728293  0.0108213117  0.2983849040
-0.6556049086 0.7550451244 -0.0094373680 -0.1062867446
-0.0143584044 0.0000304018 0.9998969123  0.0100782371
0.0           0.0          0.0           1.0
```

`T_211_to_210` 不单独维护，由 `T_210_to_211.inverse()` 生成。该规则同时适用于五雷达显示变换、桥洞检测、GNSS/INS 位姿链和 SLAM。

外参需要同时更新：

- `config/calibration.json`：运行时配置。
- `src/core/CalibrationConfig.cpp`：配置缺失或解析失败时的内置默认值。

## 雷达接收与融合范围

`mainwindow.cpp` 中 `201/213/214` 的设备读取、UDP 规则、解析器、Worker 和线程全部保留。只修改 `RadarFusionManager` 的融合选择，使最终 `fusedCloudReady` 仅包含：

```text
210 + 211
```

这样后方三雷达仍可用于状态观察和后续重新标定，不会因当前不可靠外参污染泊位检测、SLAM和融合显示。

为避免融合名单继续隐藏在 `.cpp` 局部变量中，增加一个小型、可测试的融合策略接口，`RadarFusionManager` 从该接口获取当前启用的雷达编号。

## SLAM 更新

选择性迁移 `0703/LidarGnssSlam.h/.cpp` 的算法变化，同时保留当前工程已有的命名空间、公共接口、标定读取方式和节点调用约定。

新版数据流：

```text
GNSS/INS 时间插值
  -> 组合导航相对运动预测
  -> 12 维误差状态协方差传播
  -> GICP 配准
  -> Hessian、残差和 fitness 估计观测协方差
  -> 运动方向与马氏距离检验
  -> 接受时使用完整卡尔曼增益和 Joseph 协方差更新
  -> 拒绝时只输出组合导航预测
```

保留低点数退化路径、现有外参链和日志开关。不迁移 `0703/mainwindow.cpp` 中关闭后方雷达接收的代码。

## 测试与验收

新增自动化测试验证：

1. 内置默认 `T_210_to_211` 与新标定矩阵逐元素一致。
2. `calibration.json` 加载后矩阵一致。
3. `T_211_to_210 * T_210_to_211` 为单位阵，点坐标正变换后可逆。
4. 融合策略只启用 `210/211`，明确排除 `201/213/214`。
5. 新版 SLAM 头文件和实现能在启用 SLAM 的目标中编译链接。

回归验证包括现有泊位测试、完整 `PointCloud` 构建和程序启动冒烟检查。若环境具备 PCL/nano_gicp 依赖，额外执行启用 SLAM 的完整构建；否则必须明确报告该环境限制，不用关闭 SLAM 的构建替代其验证结论。
