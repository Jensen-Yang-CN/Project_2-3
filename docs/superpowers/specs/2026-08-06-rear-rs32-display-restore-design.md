# 213/214 RS32 尾部雷达显示恢复设计

## 背景与根因

当前工程仍完整接收并解析 `201/213/214` 三路 RS 雷达数据：

```text
PCAP/在线 UDP
  -> UdpDispatcher
  -> RsLidarParser
  -> RsLidarWorker
  -> RadarFusionManager::handleRadarCloud()
```

其中 `213`、`214` 在 `mainwindow.cpp` 中明确标注为 RS 32 线雷达。两路数据未在 PCAP 读取、UDP 分流或解析阶段丢失，而是在 `RadarFusionPolicy::activeRadarIds()` 中被有意排除。当前融合名单只有 `210/211`，且唯一的 `fusedCloudReady` 输出同时服务界面显示、SLAM 和泊位检测，因此界面无法看到尾部 32 线点云。

此前排除 `201/213/214` 的原因是后方雷达外参尚未重新标定。此次只恢复 `213/214` 的界面显示，不扩大 SLAM 和泊位检测的输入范围。

## 目标

1. 在主点云界面恢复 `213`、`214` 两路 RS32 雷达数据。
2. SLAM 和泊位检测继续只使用 `210`、`211`，避免未重新标定的后方雷达污染算法结果。
3. `201` 继续接收和解析，但不进入显示、SLAM或泊位检测。
4. 保持现有 PCAP 播放、暂停、倍速、时间跳转和暂停快照行为不变。

## 非目标

- 不更新 `213/214` 外参。
- 不让 `213/214` 进入 SLAM、泊位检测或桥梁检测。
- 不恢复 `201` 的显示或算法融合。
- 不修改 RS32 数据包解码算法和设备 IP/端口配置。
- 不改变 `210` 主时钟及现有同步容差。

## 融合策略

将当前单一的雷达名单拆成两个职责明确的策略接口：

```text
显示雷达名单：210、211、213、214
算法雷达名单：210、211
```

`201` 不属于任何输出名单。

名单继续集中放在 `RadarFusionPolicy.h`，避免在界面或融合实现中散落硬编码编号。同步有效性仍使用现有 `isFrameSynchronized()` 判断。

## RadarFusionManager 输出设计

`RadarFusionManager` 继续缓存五路已解析点云，并由 `210` 帧触发一次同步融合。在同一个同步周期中生成两份结果：

1. **显示点云**
   - 遍历 `210/211/213/214`。
   - 对每路选取与 `210` 主时间戳最接近、且处于同步容差内的完整帧。
   - 使用 `RadarTransform::getConfig(id)` 中现有 `T_to_210` 变换到显示基准坐标系。
   - 仅发送给 `MultiLidarWidget::updateFusedCloud()`。

2. **算法点云**
   - 只包含显示点云中的 `210/211` 部分。
   - 继续通过现有 `onFusedCloudToBus()` 发布到融合点云总线。
   - SLAM、泊位检测和其他算法消费者不感知 `213/214`。

为避免对五路缓存执行两遍搜索和坐标转换，融合实现对显示名单只遍历一次：每路点云完成同步选择和坐标转换后总是加入显示结果；仅当编号也属于算法名单时，再加入算法结果。

## 信号与连接

`RadarFusionManager` 提供两个语义明确的输出信号：

```text
displayCloudReady(displayCloud, masterTimestamp)
algorithmCloudReady(algorithmCloud, masterTimestamp)
```

`mainwindow.cpp` 中的连接调整为：

```text
displayCloudReady
  -> MultiLidarWidget::updateFusedCloud

algorithmCloudReady
  -> MainWindow::onFusedCloudToBus
  -> SLAM / 泊位检测总线
```

旧的单一 `fusedCloudReady` 信号不再承担两个不同职责；其调用点同步迁移，避免同一份四雷达点云误入算法总线。

## 缺帧与异常处理

- `213` 或 `214` 队列为空：跳过该路，仍正常输出 `210/211`。
- `213` 或 `214` 最近帧超过同步容差：跳过该路，不复用过期帧。
- 某一路点云为空：不加入输出。
- `210` 缺失：沿用当前行为，不触发该同步周期。
- 只有显示结果非空时发送 `displayCloudReady`。
- 只有算法结果非空时发送 `algorithmCloudReady`。
- 时间跳转继续调用 `resetForPlaybackSeek()`，同时清空五路缓存，避免跳转前的 RS32 帧混入新时间线。

## 性能与内存

- 复用现有五路队列和每路最多五帧的缓存上限。
- 每个同步周期只搜索一次每路最佳帧。
- `213/214` 仅增加显示点云的坐标变换和拷贝，不重复解析原始 UDP 数据。
- 算法点云仍保持 `210/211` 的数据量，不增加泊位检测和 SLAM 负担。

3. SLAM、泊位检测和桥梁检测的数据流仍只包含 `210/211`。
4. `201` 仍被排除。
5. 时间跳转后不会出现跳转前的尾部点云残留。
6. 主程序编译成功，全部自动化回归测试通过。
