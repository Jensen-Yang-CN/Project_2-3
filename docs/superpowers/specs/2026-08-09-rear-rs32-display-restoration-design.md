# 201 尾部 32 线雷达显示恢复设计

**日期：** 2026-08-09  
**状态：** 已获用户批准，采用方案 A

## 问题与证据

目标 PCAP 为 `E:\dataset\cap_00020_20260610150748_f.pcap`。对其开始后 35 秒进行只读统计，得到：

- `192.168.1.201:6699` 有 52,500 个 1248 字节 MSOP 点云包；
- `192.168.1.201:7788` 有 31 个 1248 字节 DIFOP 包；
- `192.168.1.213` 和 `192.168.1.214` 没有数据包；
- 当前着色器将强度 50 的 `201` 点云显示为蓝色，与用户提供的正确截图一致；
- 当前显示雷达白名单只包含 `210/211/213/214`，因此已经完成解包的 `201` 帧在融合显示阶段被丢弃。

根因是上次恢复了当前 PCAP 中不存在的 `213/214`，却继续从显示输出中排除了实际尾部 32 线雷达 `201`。

## 目标行为

1. 主点云界面显示 `201/210/211/213/214` 中当前时刻存在且满足同步条件的雷达帧。
2. `201` 使用现有 `calibration.json` 外参转换到 210 坐标系，并使用强度 50 保持蓝色显示。
3. SLAM、泊位检测和感知总线继续只接收 `210/211`，不让 `201/213/214` 改变算法行为。
4. 不改动 PCAP 播放、暂停、跳转、视频解码、泊位检测和历史 SLAM 控制逻辑。

## 数据流

`201 UDP(6699/7788)` → `RsLidarParser` → `RsLidarWorker` → `RadarFusionManager` → `displayCloudReady` → `MultiLidarWidget`

算法支路保持：

`210/211` → `RadarFusionManager::algorithmCloudReady` → SLAM / 泊位检测 / 感知总线

## 实现边界

- 修改 `RadarFusionPolicy.h`，把 `201` 加入显示雷达集合。
- 同步更新融合类注释，明确显示输出和算法输出的成员范围。
- 修改现有两组雷达测试，先让它们因 `201` 被排除而失败，再修改生产代码使其通过。
- 不修改 `201` 解析器端口和型号：当前端口 `6699/7788` 与 PCAP 完全一致，驱动链路已经存在。
- 不扩大同步容差；本次根因是白名单排除，而不是同步策略。

## 验收标准

- 融合显示输出包含强度集合 `{50,100,150,200,250}`，其中 50 为 `201` 蓝色点云。
- 算法输出仍只有强度 `{150,250}`，对应 `211/210`。
- 雷达专项测试、全量 CTest 和主程序构建通过。
- 使用指定 PCAP 时，201 的蓝色尾部点云可以进入显示链路。
